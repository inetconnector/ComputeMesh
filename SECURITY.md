# Security Policy

**Current as of:** 2026-09-03

ComputeMesh is an active pre-production engineering project with real gateway, provider-agent, identity/session, shared-runtime research, billing, protected-execution and private-control-plane integration code. It is **not yet a supported public production distributed-inference service**.

For the current public-safe implementation status see `docs/CURRENT_STATUS.md`. Production ranking/policy/data live in the separate private `ComputeMesh-ControlPlane` repository.

## Supported versions

| Version | Supported |
| --- | --- |
| Development / repository `main` | engineering use only |
| Open draft P0 branches/PRs | engineering/review use only |
| Public production release | none yet |

Signed updater/release tooling exists, but that does not by itself constitute a supported production release.

## Reporting a vulnerability

Do not publish exploit details for a suspected ComputeMesh vulnerability before coordinated disclosure.

Until a dedicated security address/process is published:

1. contact the repository owner privately;
2. include the affected component/version/commit;
3. include reproduction steps and impact;
4. do not include real customer secrets or third-party personal data;
5. coordinate disclosure timing.

A future public alpha MUST provide a dedicated vulnerability-reporting channel and response policy.

## Current security boundaries

Merged foundations include gateway credentials, Ed25519 node enrollment/session authentication reference state, authenticated persistent provider-control sessions, provider execution attestations, signed private placement decisions, bounded evidence formats, durable idempotency/recovery primitives, signed update metadata and fail-closed privacy/runtime configuration.

Merged P0 confidential-execution foundations additionally include:

- a central fail-closed protected-execution gate;
- attestation-bound X25519/HKDF/AES-256-GCM protected envelopes;
- a hash-pinned NVIDIA verifier-process boundary;
- secure-memory zeroization/page-locking primitives;
- process dumpability/core-dump hardening hooks;
- request-scoped attestation/key-release contracts.

Open draft PR #76 contains additional branch-local software including protected request/response/stream transport, replay tombstones, loopback-only protected OpenAI proxying, durable confidential sessions, content-free metering, double-entry confidential escrow, unified protected gateway composition, a reduced remote confidential broker, authenticated provider-control confidential provisioning and a dedicated protected-worker HTTPS boundary.

**Those branch-local components are not a production TEE guarantee.** The final vendor-supported attestation helper, real protected hardware deployment and physical/adversarial acceptance remain mandatory.

## Important remaining boundaries

- upstream llama.cpp RPC is experimental/insecure and is **not** the ComputeMesh protected node security boundary; do not expose it to an untrusted/public network;
- public/shared development bring-up may use private networking/SSH containment, but that does not turn RPC into confidential computing;
- production node private-key storage still needs OS-backed protection and production lifecycle controls;
- active-session revocation fan-out, production service authorization/rate/resource controls and broader adversarial/fuzz/system validation remain readiness work;
- the production confidential path still needs end-to-end private broker → authenticated provider-control → protected worker wiring and complete fail-closed startup/readiness configuration;
- a real NVIDIA confidential-compute attestation helper must be built against the supported vendor stack, hash-pinned and physically validated on supported hardware;
- AMD confidential execution must not be enabled without a concrete proved CPU/CVM/device topology;
- `CRYPTO_PRIVATE` must remain unavailable until an independently validated cryptographic construction exists;
- development TLS/bearer/signing material generated by the private umbrella checkout is local-only and must not be used as production secret management;
- public providers receive only public ComputeMesh code; private control-plane ranking, pricing, reputation/fraud policy and operational data must not be deployed to provider nodes.

## Security invariants

- Provider nodes MUST NOT execute arbitrary customer code.
- User-controlled inputs MUST NOT select arbitrary host files, commands, binaries, containers or dynamic native modules.
- State-changing protocol operations MUST be replay-safe/idempotent where retryable.
- Model artifacts MUST be digest-verified before use.
- Production workers/releases/updates MUST have a defined authenticity mechanism.
- Billing entries MUST be auditable, balanced where double-entry applies and duplicate-safe.
- Privacy classes MUST be scheduler/runtime-enforced; encrypted transport is not equivalent to confidential execution.
- `CONFIDENTIAL` MUST fail closed and MUST NOT silently downgrade to `PUBLIC`.
- `CRYPTO_PRIVATE` MUST NOT be enabled from the current research blinding prototype.
- Logs/evidence MUST exclude raw prompts/outputs by default; protected ordinary logs/stores must additionally exclude reusable content keys, token IDs and semantically useful intermediate state.
- Secrets, SSH private keys, node private keys, private signing keys and operational databases MUST NOT be committed.
- Public placement/provision execution MUST fail closed on invalid/expired/untrusted private-control-plane responses/signatures where signatures are part of the contract.
- Public responses MUST NOT expose private candidate pools, losing candidates, scores, feature vectors, fraud rules, reputation internals, pricing coefficients/margins or operator decision traces.
- A remote gateway/control-plane `verified=true` flag is not a substitute for independent local verification of protected vendor evidence.
- CI success MUST NOT be described as physical TEE acceptance.

## Protected execution invariants

For `CONFIDENTIAL`, production must bind and verify at least:

- account/job identity;
- selected node identity;
- privacy class and operation;
- exact model ID;
- prompt/completion token budgets;
- fresh attestation nonce/challenge;
- measured/approved runtime digest;
- request-scoped X25519 recipient public key;
- Ed25519 content-free metering public key;
- protected data-plane TLS certificate identity;
- request and response replay/sequence state.

Protected request plaintext must be encrypted before remote network egress from the trusted local client boundary, decrypted only after validation inside the declared protected worker boundary, re-encrypted before leaving that boundary and zeroized as far as the implementation/platform permits.

## Secure development requirements

Security-sensitive changes require:

- threat-model update where applicable;
- tests for authentication/authorization and failure paths;
- negative/adversarial tests;
- bounded input sizes/resources;
- structured errors without secrets;
- review of logs/evidence/telemetry privacy;
- dependency review;
- ADR when changing trust boundaries or cryptographic choices;
- no weakening of fail-closed behavior merely to make a demo pass;
- synchronized updates to every affected authoritative document in the same branch/PR.

## Release security checklist

Before a public production-capable alpha:

- signed installer/release manifest;
- reproducible or independently verifiable release build;
- SBOM/provenance;
- staged update and rollback;
- signer/key revocation and anti-downgrade policy;
- provider workload-boundary review;
- hardened node-key storage and revocation/session behavior;
- authenticated/encrypted production public data plane;
- complete protected confidential data plane and readiness gate for `CONFIDENTIAL`;
- real supported vendor confidential-compute attestation helper and hardware acceptance before enabling `CONFIDENTIAL`;
- protocol parser fuzzing/adversarial testing;
- authn/authz/rate/resource review;
- privacy review;
- payment/ledger/settlement review;
- incident-response runbook;
- vulnerability-disclosure process;
- physical LAN/WAN runtime validation on representative hardware;
- protected provider-root/MITM/replay/substitution/dump/swap/logging acceptance tests.

## Third-party runtime warning

Third-party distributed-inference/runtime features are not automatically safe for exposure to untrusted networks. ComputeMesh must wrap, tunnel or isolate them according to its own authentication, authorization, workload and transport-security requirements before provider use.

In particular, upstream llama.cpp RPC remains a development/research transport and must not be treated as the public protected security boundary. The P0 protected path uses a dedicated authenticated/encrypted worker boundary instead.

## Dependency policy

- Pin or otherwise control production dependencies.
- Record licenses and generate release SBOM/provenance.
- Scan for known vulnerabilities.
- Minimize native/runtime dependencies on provider nodes.
- Hash-pin security-critical helper binaries where the architecture relies on a separate verifier process.
- Do not auto-enable experimental network services merely because an upstream project provides them.
